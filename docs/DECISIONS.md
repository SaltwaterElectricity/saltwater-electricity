# Project Decisions Log (ADR)

This document records the rationale behind key architectural and security decisions to prevent repeated audits and ensure long-term maintainability.

## Decision Format
- **ID**: DEC-[001]
- **Date**: YYYY-MM-DD
- **Status**: [Proposed | Accepted | Superseded]
- **Context**: What was the problem?
- **Decision**: What was chosen and why?
- **Consequences**: What are the trade-offs?

---

## Log

- **ID**: DEC-001
- **Date**: 2026-10-15
- **Status**: Accepted
- **Context**: The project has grown to include complex SMS worker logic and administrative dashboards. Dependency direction is currently implicit.
- **Decision**: Establish a strict dependency hierarchy: `UI` -> `Hooks` -> `Services` -> `Infrastructure (Firebase/SendGrid)`.
- **Consequences**: Improves testability by allowing services to be mocked; prevents UI components from directly calling Firebase Admin or SendGrid.

- **ID**: DEC-002
- **Date**: 2026-10-15
- **Status**: Accepted
- **Context**: Need a consistent way to organize UI components to avoid "Fat Pages" and monolithic files.
- **Decision**: Adopt a layered component architecture: `Primitives (ui/)` -> `Composites` -> `Feature Components` -> `Pages`.
- **Consequences**: Increases file count but reduces cognitive load per file and enables atomic testing of UI primitives.

- **ID**: DEC-003
- **Date**: 2026-10-15
- **Status**: Accepted
- **Context**: API handlers currently mix HTTP parsing and business logic.
- **Decision**: Standardize Vercel handlers to follow the pattern: `Handler` -> `Validator` -> `Use-Case Service` -> `Data Repository`.
- **Consequences**: Ensures consistency in error handling (via `SUEP`) and makes the business logic portable.

- **ID**: DEC-004
- **Date**: 2026-10-15
- **Status**: Accepted
- **Context**: SMS worker could suffer from race conditions where a stale worker (whose lease expired) attempts to transition a record to 'submitting' after a new worker has already claimed it.
- **Decision**: Combine the 'claim' and 'submit' transitions into a single atomic Firebase transaction. This ensures the token check and state transition happen as one unit.
- **Consequences**: Simplifies the state machine and eliminates the need for a separate 'claimed' status for most flows.

- **ID**: DEC-005
- **Date**: 2026-10-15
- **Status**: Accepted
- **Context**: RTDB pagination with `startAt` is inclusive. If multiple records share the same `sortKey`, a worker can enter an infinite loop processing the same record repeatedly.
- **Decision**: Implement "skip-first" logic: if the first record of a batch has a `sortKey` equal to the cursor, it is skipped. Additionally, establish a uniqueness invariant for `sortKey` (e.g., using `timestamp_deviceId`).
Consequences: Prevents infinite loops on collisions while ensuring progress.

---

- **ID**: DEC-006
- **Date**: 2026-10-15
- **Status**: Accepted
- **Context**: Need a reliable way to verify Graphify freshness to avoid relying on stale structural data.
- **Decision**: Implement a dedicated `verify_graph_freshness.js` script that compares the curated-input filesystem state against the `manifest.json` generated by Graphify, ignoring non-code files.
- **Consequences**: Provides a deterministic, executable gate for graph reliability.
